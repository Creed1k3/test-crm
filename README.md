## Что это — простыми словами

Представьте общую рабочую доску стройки. Руководитель заводит объекты и поручения, выбирает конкретного исполнителя или публикует задачу для команды. Сотрудник видит только доступную ему работу, отмечает ход выполнения, прикладывает фото и документы. Руководитель проверяет результат, принимает его или возвращает с объяснением, что нужно исправить.

Это помогает ответить на три обычных рабочих вопроса: **что нужно сделать, кто за это отвечает и что именно сдано**. Комментарии и история статусов остаются рядом с задачей.

## Возможности

| Для постановщика | Для исполнителя |
| --- | --- |
| Создавать объекты и задачи | Видеть назначенные и доступные задачи |
| Назначать сотрудника, нескольких кандидатов или всю команду | Взять общую задачу; первый отклик закрепляет её за ним |
| Следить за этапами и историей изменений | Менять статус своей задачи и отправлять её на проверку |
| Обсуждать работу в комментариях | Уточнять детали в комментариях на этапах работы |
| Смотреть приложенные фотографии и документы | Прикладывать фото и документы к работе и доработке |
| Принимать результат или возвращать на доработку с обязательной причиной | Видеть причину возврата и продолжить работу |

Поддерживаются три роли доступа: постановщик, назначенный исполнитель и участник, которому предложена задача. Удалённые записи скрываются из рабочего интерфейса; история сохраняется.

## Демо

**Приложение:** [creed1k3.github.io/test-crm](https://creed1k3.github.io/test-crm/)

Тестовые доступы передаются отдельно от публичного репозитория. Демо содержит два объекта и задачи в нескольких статусах. Можно войти постановщиком и двумя исполнителями, чтобы посмотреть разные права доступа и общий список задач.

## Как устроена защита данных

Доступ проверяет сама база данных при каждом запросе. В ней включён **RLS** — набор правил, который решает, какие строки конкретный пользователь может читать или менять. Поэтому скрыть задачу только кнопкой на экране недостаточно: прямой запрос к API тоже проходит через правила базы.

- Постановщик видит рабочие объекты и задачи команды.
- Исполнитель видит свои задачи, предложения, доступные ему общие задачи и связанные с ними объекты.
- Комментарии, история и файлы доступны только тем, кому доступна соответствующая задача.
- Файлы лежат в закрытом хранилище. Для просмотра приложение запрашивает файл в рамках активной сессии и прав пользователя.
- Смену статуса проверяют функции базы данных: роль, назначение, допустимость перехода и обязательный комментарий при возврате.
- При общей задаче база атомарно закрепляет её за первым исполнителем: параллельные запросы не должны назначить двух владельцев.
- В браузере используется только публичный ключ Supabase. Секретный ключ с полными правами в клиент не помещается.

Иными словами, исполнитель не может через интерфейс или прямой запрос присвоить себе чужую личную задачу, принять результат за руководителя или просмотреть чужой закрытый файл.

## Запуск локально

Нужны Node.js 20.19+ (или 22.12+) и проект Supabase. Создайте `.env.local` по примеру:

```env
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<publishable-key>
```

Затем установите зависимости и запустите приложение:

```sh
npm ci
npm run dev
```

### Подготовка базы

**Облачный Supabase:** примените файлы `supabase/migrations/*.sql` по порядку в SQL Editor нового проекта. В настройках Authentication отключите регистрацию и анонимный вход.

**Локальный Supabase:** нужен Docker. Из корня репозитория:

```sh
npx supabase@3.0.0 start
```

Локальный CLI применит миграции и покажет адрес проекта и ключ. Регистрация и анонимный вход отключены в `supabase/config.toml`.

### Подготовка демо-данных

В Supabase Auth вручную создайте три подтверждённых пользователя с адресами `crm-manager@example.com`, `crm-alex@example.com` и `crm-maria@example.com`, задав собственные пароли. Затем один раз выполните `supabase/demo.sql` в SQL Editor или через `psql` от имени владельца базы. Скрипт создаст профили, два объекта и задачи с разными статусами.

Для реальной базы используйте собственные учётные записи и пароли. Демо-аккаунты и пароли не хранятся в репозитории.

## Проверки и публикация

```sh
npm run build
```

Команда проверяет TypeScript и собирает приложение. GitHub Actions дополнительно поднимает тестовый Supabase, применяет миграции, запускает SQL-проверки безопасности, проверяет сценарии API (включая одновременное взятие общей задачи и доступ к Storage) и собирает фронтенд. Успешная проверка основной ветки публикует приложение на GitHub Pages.

Дополнительные проверки базы можно выполнить после запуска локального Supabase:

```sh
psql "postgresql://postgres:postgres@127.0.0.1:54322/postgres" -v ON_ERROR_STOP=1 \
  -f supabase/tests/security.sql \
  -f supabase/tests/collaboration_security.sql
```

Основные каталоги:

```text
src/
  auth/                 вход и сессия пользователя
  components/           общие элементы интерфейса
  features/objects/     объекты и их страницы
  features/tasks/       задачи, формы, списки и обсуждение
  lib/                  клиент Supabase, типы и загрузка данных
supabase/
  migrations/           схема базы, RLS-политики и функции
  tests/                проверки доступа и рабочих сценариев
  demo.sql              начальные данные демонстрации
.github/workflows/      проверки и публикация
```

## Решения и расширения относительно ТЗ

Это небольшое тестовое приложение, поэтому неоднозначности закрыты простыми правилами:

- Добавлены комментарии к задаче на разных этапах, чтобы обсуждение и причина возврата не терялись.
- Добавлены фотографии и документы до 20 МБ. Это позволяет исполнителю показать, что именно сдано, а постановщику — посмотреть результат перед приёмкой.
- Помимо назначения одному исполнителю, есть задачи для выбранных кандидатов и общие задачи. Задачу может взять первый исполнитель, после чего она закрепляется за ним и пропадает из доступных для других.
- При возврате на доработку причина обязательна; кнопка возврата выделена красным и открывает отдельный ввод комментария.
- Роль пользователя задаётся в профиле администратором базы. Открытой регистрации нет.
- Удаление объектов и задач логическое: записи скрываются из обычного интерфейса, но история не стирается. Восстановление через интерфейс не сделано.
- При переназначении задачи новый исполнитель получает её историю, а прежний теряет доступ к задаче и её материалам.
- Исполнитель видит своё имя и необходимые имена участников доступных задач; список сотрудников для назначения доступен постановщику. Email и служебные сведения Auth через CRM не раскрываются.
- Поля описания и вложения необязательны. Созданная задача сразу получает статус «Новая»; задача для кандидатов становится личной после взятия.

Расширения намеренно относятся к рабочему потоку задачи: помогают назначать работу, обсуждать её и проверять фактический результат. Остальные функции ограничены объёмом тестового задания.

- React и TypeScript, сборка Vite.

- PostgreSQL, RLS и SQL-функции для правил доступа и переходов состояний.
- Supabase Storage для приватных вложений.
