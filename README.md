# Объекты и задачи

Мини-CRM для строительной компании на React, TypeScript и Supabase. Постановщик создаёт объекты и задачи, назначает исполнителей и проверяет результат. Исполнитель видит свои задачи, берёт их в работу и отправляет на проверку.

Постановщик может назначить задачу одному человеку, предложить её выбранным исполнителям или открыть для всех исполнителей. Предложения видны в разделе «Доступные задачи». Как только один человек берёт задачу, она становится его личной задачей и исчезает из выдачи для остальных.

В карточке можно оставлять комментарии на любом этапе. Исполнитель может приложить фотографии и документы во время работы и доработки, а постановщик видит их при проверке. Фото доступны для просмотра в карточке. Вложения до 20 МБ хранятся в приватном Supabase Storage, доступ к ним зависит от доступа к задаче.

[Демо на GitHub Pages](https://creed1k3.github.io/test-crm/). Доступы к демо передаются отдельно.

## Запуск

Понадобятся Node.js 24 и проект Supabase. Скопируйте `.env.example` в `.env.local` и укажите URL проекта и публичный ключ из Supabase. Затем запустите:

```sh
npm ci
npm run dev
```

Подготовьте базу одним из способов:

- **Облако.** Выполните файлы `supabase/migrations/*.sql` по порядку в SQL Editor нового проекта. В Authentication → Sign In / Providers отключите регистрацию и анонимный вход.
- **Локально.** С запущенным Docker выполните `npx supabase@3.0.0 start` из корня репозитория. CLI применит миграцию и выведет URL и публичный ключ. Регистрация и анонимный вход отключены в `supabase/config.toml`.

Для демо вручную создайте в Supabase Auth подтверждённые email-аккаунты `crm-manager@example.com`, `crm-alex@example.com` и `crm-maria@example.com` со своими паролями. Один раз выполните `supabase/demo.sql` в SQL Editor или через `psql` от владельца базы. Скрипт создаст профили, два объекта и задачи с историей.

## Как защищены данные

Роль хранится в `profiles` и назначается администратором базы. Политики доступа PostgreSQL (RLS) применяются к каждому запросу, включая запросы напрямую к API. Постановщик видит все рабочие записи. Исполнитель видит назначенные ему задачи, доступные предложения и связанные объекты. История, комментарии и вложения наследуют видимость задачи.

Статус меняет функция `transition_task`. Она проверяет текущий статус, роль и назначение, а при возврате требует комментарий. Функция `claim_task` блокирует строку задачи, пока назначает первого исполнителя и записывает переход в историю. Прямое изменение статуса и запись в журнал через API запрещены. Клиент использует только публичный ключ и сессию пользователя.

## Проверки

- `npm run build` проверяет типы и собирает фронтенд.
- `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/security.sql` запускает SQL-проверки под разными ролями. Запускайте от владельца базы после миграции. Тестовые записи откатываются в конце.
- GitHub Actions поднимает локальный Supabase и проверяет два одновременных запроса на взятие задачи, видимость комментариев и доступ к файлам через настоящий API.
- Для ручной проверки откройте «ЖК „Северный“» от лица обоих исполнителей. Каждый увидит только свои задачи на общей стройке. «Склад „Восточный“» доступен только Марии и постановщику.

## Решения по ТЗ

- Удаление логическое. Объект и его задачи исчезают из CRM, журнал остаётся в базе. Восстановление через интерфейс не предусмотрено.
- После переназначения новый исполнитель видит всю историю задачи, прежний теряет к ней доступ.
- При создании задача получает статус «Новая», и это событие сразу записывается в историю. В личной задаче исполнитель обязателен, у предложения появляется при взятии. Описание и вложения можно оставить пустыми.
- Исполнитель видит свой профиль и имена участников доступных задач. Постановщик видит список сотрудников для назначения. Email и сведения Supabase Auth через CRM недоступны.
